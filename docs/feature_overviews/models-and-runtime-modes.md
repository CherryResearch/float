models and runtime modes decide where float's intelligence comes from for a given task. A chat can run through a cloud API, a local model on the device, or a separate server on the network, and float can also route local work through managed provider runtimes such as LM Studio and Ollama.

For the user, this is really about tradeoffs. One mode might be better for privacy, another for speed, another for capability, and another for hardware convenience. The important distinction is that local means the work is happening on the user's machine or through a locally managed runtime, while Server/LAN means float is talking to some other server that already exists.

In practice there are three separate categories to keep straight: direct local Transformers checkpoints running inside Float, managed local providers such as LM Studio or Ollama that Float talks to over an OpenAI-compatible interface, and `Server/LAN` targets that are already-running remote or networked servers. Those paths overlap in the UI, but they are not identical in maturity or configuration. This flexibility is one of float's core design goals, but feature parity across all runtimes is still a work in progress and some runtime paths need more live verification than others. The public references for the current shipped surface are `README.md`, `docs/environment setup.md`, and `docs/api_reference.md`.

Server/LAN presets make repeat connections easier without moving provider secrets into browser state. Float includes localhost LM Studio and Ollama presets plus hosted OpenAI-compatible choices for Tinker / Inkling, Anthropic / Claude, Gemini, and OpenRouter, and users can save additional endpoints with a named environment variable for bearer auth. Tinker is the account-aware exception to generic model discovery: its preset lists supported base models and sampler checkpoints, so a `tinker://.../sampler_weights/...` custom fine-tune can be selected directly. Inference still goes through the shared OpenAI-compatible chat lane; the direct Claude preset therefore follows Anthropic's compatibility-layer limits rather than exposing every native Claude feature. Providers with only a native, incompatible API need a compatibility gateway. Grok is not advertised as a preset; manually configured or routed Grok targets carry a visible trust warning.

Chat reasoning can use the provider default (`auto`), named `none`, `minimal`, `low`, `medium`, `high`, and `xhigh` levels, or a custom effort from `0` through `0.99`. Tinker / Inkling receives the exact custom value; other recognized reasoning models round custom values to the nearest named level so unsupported granular controls do not break the turn. Reasoning effort and maximum output are independent: output can use the provider default, a preset from 4K through 1M, or a custom value up to 2M. When model inventory reports a context window or maximum output, Chat displays it without inventing missing limits; Tinker's current SDK reports context length but not a separate output maximum. Explicit output plus the prompt must fit within the model context. Response metadata records the requested and effective effort, whether rounding occurred, the selected output limit or provider default, the finish reason, and whether the answer stopped at a token cap. Float also tells the agent which underlying runtime model generated the turn while keeping Float as the product and agent identity.
